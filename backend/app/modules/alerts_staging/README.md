# Alert and Notification System — `alerts_staging` Module

## Overview

The `alerts_staging` module is the clinical alert backbone of PrescpHealth. It generates,
routes, delivers, and escalates alerts for clinicians based on patient measurements, computed
risk scores, and forecast trajectories.

All alerts are tenant-isolated, HIPAA-compliant, and carry a full lifecycle audit trail.

---

## Architecture

```
Domain Events (event_bus)
        │
        ▼
 AlertRulesEngine ──────── AlertThreshold (DB)
        │
        │ create_alert()
        ▼
  AlertService ──────────── Alert (DB)
        │
        │ dispatch_alert_task.delay()
        ▼
  [Celery Worker]
        │
        ▼
  AlertDispatcher
   ├─ send_in_app()      ← Always first; marks alert "in-app visible"
   ├─ send_email()       ← STUB → SendGrid (future)
   ├─ send_sms()         ← STUB → Twilio (future)
   └─ send_whatsapp()    ← STUB → WhatsApp Business API (future)
        │
  [Celery Beat — every 5 min]
        │
        ▼
  EscalationService
   └─ check_and_escalate()
       ├─ Level 0 → 1: 15-min timeout → Doctor
       ├─ Level 1 → 2: 30-min timeout → Clinic Admin
       └─ Level 2: Max — resolve as unacknowledged
```

## Data Models

### `Alert`
Central alert record. Tracks the full lifecycle from creation to resolution.

| Column              | Type        | Description                                         |
|---------------------|-------------|-----------------------------------------------------|
| id                  | UUID        | Primary key                                         |
| tenant_id           | UUID        | Tenant isolation (RLS-enforced)                     |
| patient_id          | UUID        | Patient the alert concerns                          |
| alert_type          | String      | Classification (threshold_breach, risk_critical...) |
| severity            | String      | critical / high / moderate / low / info             |
| title               | String      | Short human-readable title                          |
| message             | Text        | Clinical description (PHI — not logged)             |
| payload             | JSONB       | Structured clinical context (PHI — not logged)      |
| status              | String      | active / acknowledged / escalated / resolved        |
| acknowledged_at     | Timestamp   | When a clinician acknowledged the alert             |
| acknowledged_by     | UUID        | Which user acknowledged (UUID only, not name)       |
| escalation_level    | Integer     | 0=initial, 1=doctor, 2=clinic_admin                 |
| channels_dispatched | JSONB array | List of channels attempted                          |
| dispatch_status     | JSONB dict  | Per-channel delivery status                         |

### `AlertThreshold`
Configurable rules that define when an alert fires. Supports per-patient overrides
and tenant-wide defaults (patient_id IS NULL).

| Column           | Type    | Description                                   |
|------------------|---------|-----------------------------------------------|
| patient_id       | UUID?   | NULL = tenant-wide default                    |
| measurement_type | String? | For measurement-based thresholds              |
| disease          | String? | For risk-score-based thresholds               |
| condition        | String  | above / below / enters_stratum                |
| threshold_value  | Float?  | Numeric threshold for above/below             |
| target_stratum   | String? | Stratum name for enters_stratum condition      |
| severity         | String  | Severity of alerts generated by this threshold|
| is_active        | Boolean | Soft-delete flag                              |
| created_by       | UUID    | Clinician who configured this threshold        |

### `EscalationRecord`
Immutable audit trail of each escalation event. Never updated after insert.

| Column          | Type      | Description                            |
|-----------------|-----------|----------------------------------------|
| alert_id        | UUID      | Parent alert reference                 |
| from_level      | Integer   | Previous escalation level              |
| to_level        | Integer   | New escalation level                   |
| escalated_at    | Timestamp | When escalation occurred               |
| target_user_id  | UUID      | Who received the escalation            |
| reason          | String    | e.g. "unacknowledged_timeout"          |

## Event Subscriptions

The `AlertRulesEngine` subscribes to three domain events via the central `event_bus`:

| Event Type            | Handler                    | What It Checks                            |
|-----------------------|----------------------------|-------------------------------------------|
| `measurement_saved`   | `evaluate_measurement()`   | Measurement above/below thresholds        |
| `risk_score_computed` | `evaluate_risk_score()`    | Risk stratum transitions                  |
| `forecast_completed`  | `evaluate_forecast()`      | Projected future threshold crossings      |

Each handler creates its own DB session and runs independently of any HTTP request context.

## Alert Lifecycle

```
                    ┌──────────┐
                    │  ACTIVE  │ ◄── Created on threshold breach
                    └────┬─────┘
                         │
           ┌─────────────┼──────────────────┐
           │             │                  │
           ▼             ▼                  ▼
    ┌──────────┐  ┌──────────────┐  ┌──────────┐
    │ACKNOWLEDGED│  │  ESCALATED   │  │ EXPIRED  │
    │(clinician) │  │(timeout hit) │  │(low only)│
    └──────────┘  └──────┬───────┘  └──────────┘
                         │
                         ▼
                   ┌──────────┐
                   │ RESOLVED │
                   └──────────┘
```

- **ACTIVE → ACKNOWLEDGED**: Clinician calls `PUT /api/v1/alerts/{id}/acknowledge`
- **ACTIVE → ESCALATED**: Celery beat task detects timeout; EscalationService bumps level
- **ESCALATED → RESOLVED**: Max level reached with no acknowledgment (auto-resolved)
- **ACTIVE → EXPIRED**: Low/info severity alerts age out (future feature)

## Escalation Chain

| Level | Recipient     | Timeout   | Trigger              |
|-------|---------------|-----------|----------------------|
| 0     | Nurse         | 15 min    | Initial assignment   |
| 1     | Doctor        | 30 min    | Level 0 timeout      |
| 2     | Clinic Admin  | 30 min    | Level 1 timeout      |
| Max   | —             | —         | Auto-resolve as unack|

The escalation check runs every **5 minutes** via `check_escalations_task`.
Only **CRITICAL** and **HIGH** severity alerts are escalated.

## Dispatch Channels and Retry Policy

| Channel   | Implementation | Retry Window | Notes                              |
|-----------|---------------|--------------|-------------------------------------|
| in_app    | Native         | Immediate    | Always succeeds; no external call   |
| email     | STUB→SendGrid  | 24 hours     | Resolved via user profile service   |
| sms       | STUB→Twilio    | 6 hours      | Phone number resolved at send time  |
| whatsapp  | STUB→WA API   | 6 hours      | Future; template approval required  |

**Retry backoff**: 30s → 2min → 8min → 30min → 90min (exponential: `30 * 4^n`)
**Max retries**: 5 per dispatch task

## HIPAA Compliance Notes

1. **Cache-Control: no-store** — Set on every response; prevents PHI caching in proxies or browsers.
2. **PHI-safe logging** — Only UUIDs appear in logs (alert_id, patient_id, tenant_id).
   Never log: patient names, measurements, risk scores, alert message content, or payload values.
3. **Row-Level Security (RLS)** — All three tables enforce `tenant_id` isolation at the
   PostgreSQL level via `tenant_isolation_policy`. Application-layer filtering is a second layer.
4. **Audit trail** — All mutations (create, acknowledge, configure threshold, escalate, deactivate)
   are logged via `AuditService`.
5. **Immutable escalation records** — `EscalationRecord` is never updated; it is an append-only
   audit trail.
6. **Payload isolation** — Clinical data (measurements, scores) is stored in JSONB `payload`
   and `message` fields, which are never written to logs or monitoring systems.
